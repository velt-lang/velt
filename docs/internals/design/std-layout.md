# Standard library layout: `velt/…` modules, folders, `index.vlt`

Status: in progress, one pull request (#1946). Owners: std (the layout), the `veltc` loader (specifiers
and visibility), `std-lint` (the rules, written in Velt). The move itself is a one-time script
(§8).

## Why now

The standard library becomes the API other people build on. Velt is new, so this is the one
point where breaking every import costs only us. After it ships, every rename is a
deprecation cycle. This design fixes the structure once, with rules a tool enforces, and does
the mechanical move with a script so open branches can replay it instead of resolving
conflicts by hand.

## What is wrong today (measured on `main`, 2026-10-30)

| Problem | Evidence |
|---|---|
| A flat root | 51 `.vlt` files directly in `std/` next to 24 folders; `fetch.vlt` + `fetch/`, `http.vlt` + `http/`, `sqlite.vlt` + `sqlite/` are the Rust-2015 `foo.rs` + `foo/` pattern. |
| No areas | `udp`, `dns`, `net`, `http`, `websocket`, `url`, `fetch` are siblings of `arena`, `symbol`, `this_fn`. Nothing says "networking". |
| Internals look public | `net_bytes`, `import_meta`, `this_fn`, `number/*`, `sort/*`, `record/*`, `json/scan`, `url/encode` can all be imported as `velt:…`; "internal" exists only as README prose. The LSP even ships a hard-coded list to hide some (`crates/veltc/src/commands/lsp.rs:312`). |
| Global-only modules | `symbol`, `proxy`, `dom_exception`, `string_builder`, `typed_array` exist to provide globals but are also importable modules, so there are two ways to reach the same thing. |
| Big files, many types per file | 72 files over the 400 lines std's README asks for, 31 over 600 (`compress/inflate/tables.vlt` 2187, `collections/concurrent_map.vlt` 1282, `crypto.vlt` 1003, `proxy.vlt` 978). `jsx/attrs/svg.vlt` exports 27 types, `prelude/iter.vlt` 14. Nothing checks the 400: the file-size rule (`crates/xtask/src/file_size.rs`) covers only `crates/**/*.rs`. |
| Load order in file names | `prelude/z_dynamic.vlt`, `zzz_adapt.vlt`, `zzzz_any_methods.vlt`, `zzzzz_any_ops.vlt`: the loader reads the prelude in directory order. |
| The compiler knows std paths everywhere | 77 non-test compiler sources contain `"std/…"` or `"velt:…"` literals (lazy std's `EAGER` list, lowering's builtin lookups, mangling, the doc site). Each move today means hunting them. |
| Specifier | `velt/fs` cannot be resolved by `tsc`, so `velt check --ts-compat` has to reject every std import (`velt-import` rule). |

## Decisions

### 1. Imports are `velt/<area>[/<module>]`

```ts ignore
import { readFile } from "velt/fs";
import { Deque, BTreeMap } from "velt/collections";
import { Headers } from "velt/net/http";
```

- `velt` is a package name the toolchain provides. The loader resolves `velt/…` to `std/`
  before looking at dependencies. `vpm` refuses `velt` as a dependency or package name, and we
  reserve `velt` on npm and on the Velt registry.
- Why not `velt:`: `velt/x` is an ordinary package path, so a published `velt` type package
  (declarations generated by `velt doc`, an `exports` map per module) lets `tsc`, editors and
  bundlers resolve std imports. That turns the `velt-import` ts-compat error into "install the
  types". `jsxImportSource: "velt/jsx"` works in a stock `tsconfig.json` too.
- `velt:x` stops resolving. It becomes a compile error: `` `velt:` specifiers were removed;
  std modules are `velt/<module>` ``, naming the module that replaced `x` (a table in the
  compiler, `loader/moved.rs`, which also notes it on `cannot find module velt/<old name>`; a module
  that left std names its package). There is no alias period: we have no outside users to
  protect, and two spellings would end up in docs and examples forever.
- `vitest` keeps resolving to `velt/test`.

### 2. Every module is a folder, and its `index.vlt` is its public surface

```
std/net/http/
  index.vlt        ← the public API of velt/net/http: explicit re-exports, the module doc
  fetch.vlt        ← implementation, owned by the module
  serve.vlt
  headers.vlt
  client/          ← implementation folder (no index.vlt), still owned by velt/net/http
  server/
    index.vlt      ← a submodule: velt/net/http/server
```

The rules, all checked by the std lint (§6):

1. **A folder with an `index.vlt` is a module.** Its import path is the folder's path below
   `std/`.
2. **Every other `.vlt` file belongs to the nearest folder above it that has an `index.vlt`.**
   A file with no such folder is an error (only `prelude/` and `lang/` are exempt, §4). This
   makes "internal" structural: a file outside an `index.vlt` is never imported by user code.
3. **A folder without an `index.vlt` is either a namespace or an implementation folder.** A
   namespace holds only modules (`std/net/` holds the folders `http/`, `udp/` … and its own
   `index.vlt` for TCP). An implementation folder sits inside a module and holds its files
   (`collections/btree/`).
4. **`index.vlt` re-exports by name**: `export { Deque } from "./deque";`. No `export *`, no
   implementation in `index.vlt` beyond small glue: the file *is* the reviewable public API, and
   `velt doc` documents a module from it.
5. **No `x.vlt` next to an `x/` folder.** The pair becomes `x/index.vlt` (module) or moves
   into `x/` (implementation).
6. **Every public name has one import path.** If `velt/net/http` exports `Headers`, no other
   module does. Globals (`fetch`, `URL`, `Set`, `RegExp` …) are also importable from their
   module, and that is the only exception.

User code may import only modules (rule 1) outside `prelude/` and `lang/`. std code may import
any std file by its `velt/` path. The loader enforces both (§5).

### 3. Areas

The top level is short and named for what a program does, after Go's `net/http`,
`encoding/json` and .NET's `System.Net.Http`, `System.Text.Json`. Names stay Node's where a TS
programmer looks for them (`fs`, `path`, `os`, `process`). An area is usually *one* module with
one `index.vlt`, like a .NET namespace. Submodules exist only for large or optional parts that
have their own docs page.

**Not in std** (std is the core; these are libraries, and they move to their own repositories
later). Each becomes a package under the repository's `packages/`, written only on public std
APIs (no `__intrinsic_*`, no `declare`d runtime functions it does not own):

| Package | From |
|---|---|
| `packages/sqlite` | the SQLite driver (`velt/sqlite` + crate `velt_std_sqlite` as its native part), merged with today's prototype `packages/sqlite`; the pure-Velt query engine (#1726) comes along |
| `packages/postgres` | `velt/postgres` + crate `velt_std_postgres` |
| `packages/redis` | `velt/redis` + crate `velt_std_redis` |

| `packages/http-server` | the HTTP server written in Velt (#1533, HTTP/1.1, HTTP/2, TLS): `"http-server"` with `serve` (web-standard handlers, `(req: Request) => Response`) and the lower-level `serveHttp`, `HttpRequest`, `HttpResponse`; `"http-server/websocket"`, the WebSocket server (`upgradeWebSocket`, on the client's `WebSocket` over an upgraded stream) |

The HTTP server leaves std too (decided 2026-10-30, after first keeping it): a server is a
library, and the one Velt ships is the proof that anyone can write one on public APIs. Moving
it out removes what only std could do for it:

- `Request` and `Response` gain public API for a server: a `Request` over a body read when
  asked for (`RequestSource`), a `Response`'s parts read for writing (status, headers, body
  kind), and `101 Switching Protocols`. No `private` member is called from another module.
- Hot reload's graceful stop is `velt/dev` (`stopRequested`, `drained`), not the runtime
  functions declared in the server.
- HPACK and HTTP/2 frames are `velt/net/http/hpack`, which the `fetch` client uses too.
- The concurrency checks for callbacks that run on other threads (a handler must not change
  what it captures, nor capture a resource) apply to any function outside the caller's
  package, not to std's functions only; the handler error tests check that rule with a
  function of their own that spawns its callback.

The hyper-based server (`velt:http` `serve`, `crates/velt_rt/src/http/`, the `hyper` crates) is
removed. The examples and `velt new` templates depend on the package by path, as the sqlite
examples do.

As built (commit 6): each package has `src/lib.vlt` (its API, named re-exports), `native/` (the
crate, outside the cargo workspace and the runtime), `tests/` (`velt test`, run for every package
by `crates/veltc/tests/packages.rs`), `README.md` and `docs/` (the native ABI; the engine for
sqlite). packages/sqlite keeps the driver's API (the prototype's is gone: its README maps one to
the other) and has the engine as `sqlite/engine`, sharing the driver's `SqliteError`. What the
drivers took from std-only intrinsics is public std API now: velt/db's `decodeRows`, `decodeRow`
and `bindParams`, velt/native's `errorCodeName`, `Array.reserve`/`truncate` and velt/encoding's
`utf8ByteAt`/`utf8Length` (the last ones existed).

Every row maps to entries in `layout.vlt`; that file is authoritative where they differ. The
whole tree after the move is in the appendix.

### 4. `prelude/` and `lang/` are never imported

- `std/prelude/` stays the implicit prelude. Its load order is an explicit list in
  `std/prelude/index.vlt` (`import "./array"; …`), which the loader follows (done: the `z_`…`zzzzz_`
  prefixes are gone; `velt_common::std_modules::prelude_order` reads the list, and a test checks
  that it names every prelude file once).
- `std/lang/` is new: what implements the language and its globals, which no program imports:
  `symbol`, `proxy`, `record`, `this_fn`, `import_meta`, `dom_exception`, `typed_array`,
  `number` (float parsing), `sort` (the sort algorithms), `intrinsics` (the compiler's
  intrinsics, declared: §10). Each is a folder; since nothing
  imports `lang/`, its folders need no `index.vlt`. `prelude/global/*.vlt` re-exports from here
  as today.

### 5. The compiler names std modules in one place

Before anything moves, the `"std/…"` literals in the compiler (77 files) move into one table of
well-known std modules: lazy std's `EAGER` and `JSON_GLUE`, lowering's lookups
(`std/fetch/response`, `std/record/`, `std/collections/`, `std/simd`, `std/json/writer`), the
JSX default, the LSP's hidden list (which rule 2 makes unnecessary). Every other crate reads the
table. `velt_common` is the natural home and is a contract: the first PR says so (CLAUDE.md rule
1). After that, a move changes that one table, and the tool rewrites it (§7).

Done: `crates/velt_common/src/std_modules.rs` is the table. Each entry names a module by its path
below the std root (`lang_proxy => "lang/proxy"`); the macros `std_module!`, `std_item!`,
`std_dir!` and `std_specifier!` spell its canonical path, a definition's qualified name, its
folder prefix and its import specifier as literals, and a test checks that every entry names a
file of `std/`. The same module holds the prelude's order (`prelude_order`) and the visibility
rule (`importable`, `owner`), which the loader and the language server share; the LSP offers
exactly the modules the rule lets a program import, so its own list of hidden modules is gone.

The loader gains:

- `velt/` resolution to std (with the folder-module lookup it already has for
  `std/net/index.vlt`, `crates/veltc/src/loader/locate.rs:182`);
- the visibility rule: from user code, the target must be an `index.vlt` outside `prelude/` and
  `lang/`; otherwise "`velt/json/scan` is internal to `velt/encoding/json`" (done: user code is
  any module not loaded from std, packages included; the error notes the module to import from;
  the import the parser adds for `import.meta` is exempt, and so are std's test files, which
  `velt test std/` imports; `velt/sqlite`, `velt/postgres` and `velt/redis` stay importable whole
  until they move to `packages/`);
- the error for a `velt:` specifier (§1);
- the explicit prelude order.

### 6. Quality rules for std code, checked by `std-lint`

`std-lint` runs in `scripts/check.sh` when `std/` changes and in
`cargo xtask precheck`. It checks the layout rules of §2 and:

| Rule | Limit |
|---|---|
| File size | 400 lines (tables generated by a script: 2,500, marked by a `// generated by scripts/<script>` header). The current oversized files are listed in `layout.vlt` `oversize` with the PR that splits them, as `ALLOWED_OVERSIZE` does for Rust. The list may only shrink. |
| One primary type per file | A file exports at most one class (or class-like interface) and names the file after it: `Deque` in `deque.vlt`. Its small helpers may come along: option interfaces, a result union, its iterator. Type-only files (`types.vlt`) and the module's errors (`errors.vlt`) are the exceptions. |
| Header | The first line is `// velt/<module>: <role>.` (`// velt/<module> (internal): …` for files that are not `index.vlt`). |
| Doc comments | Every name an `index.vlt` exports has a doc comment (docs/internals/design/doc-comments.md). `velt doc --std` runs with warnings as errors. |
| Errors | One error class per module, or a few in `errors.vlt`, extending `Error`; messages as in docs/std/README.md "Conventions". |
| Names | Files and folders `snake_case`; `*Sync` for blocking twins; Node's name where Node has the function. |
| No duplicate exports | Rule 6 of §2, across all `index.vlt`. |
| Docs mirror the tree | `docs/std/<module path>.md` exists for every module (`docs/std/net/http.md`), with a page per part of a module below it (`docs/std/time/datetime.md`); the site lists docs/std by following the tree (`* = ../std/` in `docs/site/pages.txt`). |
| Tests mirror the tree | Every module has end-to-end tests under `tests/golden/std/<module path>/`. |

**How to split a file.** The size limit only detects the problem; the goal is files that each
answer one question. Split by responsibility, never by line count:

- **A class gets a file of its own**, named after it, with its small companions (its options
  interface, its iterator).
- **Free functions group by the operation family they implement**, the way Node's documentation
  groups them: opening and closing, reading, writing, metadata. `fs/fd.vlt` (490 lines, no
  classes) becomes `fs/fd/system.vlt` (the `declare system function` bindings and the C
  layouts), `fs/errors.vlt` (errno → Node's `IoError`, shared by all of `velt/fs`),
  `fs/fd/args.vlt` (Node's argument checks and their `RangeError`/`TypeError` messages),
  `fs/fd/open.vlt`, `fs/fd/read.vlt`, `fs/fd/write.vlt` and `fs/fd/sync.vlt`.
- **Native bindings** (`declare function velt_rt_*`, `declare system function`) sit in one file
  per module (`system.vlt` or `rt.vlt`), so a module's native surface is reviewable in one place
  and its other files are plain Velt.
- **Helpers two files need** become a file of their own that both import, rather than a copy or
  a cross-import between two operation files.
- **Tables** (constants, generated data) are files of their own; a generated one says so in its
  header (`// Generated by scripts/…`) and is exempt from the size limit.
- **Nothing is split to hide it from the loader.** A module that existed only so that importing
  the area did not compile it (`velt:fs/fd`) folds back into its area: the loader loads an
  index's re-exports only for the names a program imports (§2), so `openSync` is exported from
  `velt/fs`, where Node has it, and costs nothing to a program that does not use it.
- **An index.vlt holds no code**: what an area's index implemented (`readFile` in
  `fs/index.vlt`) moves to a file of the area, and the index lists it.

### 7. Rules for agents and contributors, enforced by `precheck`

Most std changes are written by agents, and an agent follows what fails, not what a README
says. So every rule above that a machine can check runs in `cargo xtask precheck` (the
pre-push hook) on the changed std files, and each failure message says what to do, not just
what is wrong:

| Check in `precheck` | Message (example) |
|---|---|
| A new `.vlt` file directly in `std/`, or outside every module | `std/foo.vlt: std files live in a module folder; put it in std/<area>/ (docs/internals/design/std-layout.md §3 lists the areas)` |
| A `velt:` specifier anywhere | `use "velt/fs" (velt: specifiers were removed)`, with the target from `layout.vlt` |
| A user-facing file (tests, examples, docs) imports a non-index std file | `velt/json/scan is internal to velt/encoding/json; import from "velt/encoding/json"` |
| A new export in an implementation file that no `index.vlt` re-exports, or a re-export without a doc comment | `Deque is exported from collections/deque.vlt but not re-exported by collections/index.vlt` |
| `export *` in an `index.vlt` | `re-export by name so the module's API is reviewable` |
| A file over 400 lines, or one more exported class in a file | `split by type: one exported class per file (docs/internals/design/std-layout.md §6)` |
| A module (an `index.vlt`) without `docs/std/<path>.md`, or without tests: an end-to-end test that imports it (`tests/golden`, `tests/std`) or white-box tests in its folder | `velt/text has no page: write docs/std/text.md (docs/std mirrors std's tree; the site lists it by itself)` |
| A file added to an allow list in `layout.vlt` (`oversize` …) | `the allow lists only shrink` |
| Header line missing or naming the wrong module | the expected first line |

These checks look only at changed files, so they cost almost nothing on top of today's
`precheck`; `std-lint` over all of std runs in `check.sh`.

To make the right thing the easy thing:

- `std-lint new <module path>` scaffolds a module: `index.vlt` with the header, the docs
  page and a golden test folder.
- **CLAUDE.md** "Rules for agents" gets one rule: *std code lives in module folders; a module's
  API is its `index.vlt`; one exported class per file; run `std-lint new` for a new
  module; the layout and its rules: docs/internals/design/std-layout.md*.
- **CONTRIBUTING.md** "Coding standards" gets a "Standard library" subsection with the rules of
  §2 and §6, replacing the "Rules for std code" section of `std/README.md`, which then only
  points there.
- **The pull request self-check** (CONTRIBUTING.md "Before opening a pull request") gets:
  *std API change: `index.vlt` re-export with a doc comment, the docs page, a golden test*.

### 8. The layout is Velt data, and the move is a one-time Velt script

Velt describes its own configuration in Velt: `package.vlt` is a typed data file that tools
parse and never run. The layout follows that pattern:
[`scripts/std-layout/layout.vlt`](../../../scripts/std-layout/layout.vlt) is
`export const layout: StdLayout = { … }`, typed by
[`types.vlt`](../../../scripts/std-layout/types.vlt): `dirs` and `files` (old → new below
`std/`), `leaving` (what goes to `packages/` or away), `newIndex` (area modules whose
`index.vlt` is written by hand), `modules` (old public specifier → its module, `null` for
globals) and `docs`.

[`scripts/std-layout/main.vlt`](../../../scripts/std-layout/main.vlt), written in Velt on std,
does the mechanical part: `git mv` of every file (history follows), then every `velt:` specifier
rewritten (inside std to the moved file's own path, elsewhere to the module of `modules`, names
that moved to another module per `names`), `std/<file>.vlt` paths in comments, docs and expected
outputs, the compiler's `"std/<module>"` names and the conditional globals' `load when` lines. It
stops if a std file has no rule, and prints what it could not map.

The pull requests open today merge to `main` first, so the branch is built to be **replayed**:

- the commits before the move (this design, the script) are ordinary commits;
- the move itself is one commit, *generated* by the script plus `velt fmt std examples`, never
  edited by hand (subject `std: the move to velt/<area> modules (generated by
  scripts/std-layout)`);
- everything hand-written (the new `index.vlt` files, the compiler, the `velt/io` split, the
  later commits) comes after it.

[`scripts/std-layout/replay.sh`](../../../scripts/std-layout/replay.sh) moves the branch onto a
newer `main`: it cherry-picks the commits before the generated one, runs the script again (so
what merged meanwhile is moved and rewritten too: a file edited on `main` at its old path, a new
file in a folder that moves, a new test with `velt:` imports), and cherry-picks the hand-written
commits. A new std file no rule covers stops it with its name: add the rule to `layout.vlt` in the
`scripts:` commit and run it again. Before the pull request merges, the script, `layout.vlt` and
`replay.sh` are deleted (this document keeps the tree).

The rules of §2 and §6 stay checked after that by a permanent `std-lint` (in Velt, run by
`precheck` and `check.sh`, §7).

### 9. White-box tests of std internals

About 40 test files outside std import std internals today (`tests/golden/std/*`,
`tests/std/http`, `tests/std/fetch`, `tests/std/websocket`, the JSX attribute error goldens),
for example the B+ tree's invariant checks. Rule 2 forbids that from user code, and it should:
a test that reaches into internals belongs next to them. So:

- **Black-box tests** (the public API) stay end-to-end under `tests/golden/std/<module path>/`.
- **White-box tests** move next to the code as `std/<module>/<name>.test.vlt` (Vitest's
  convention, which `velt test` already follows), run in the gate with `velt test std/`, and
  are left out of the toolchain's packaged std.

Done: the loader loads std's test files as std code (they import internals by their `velt/`
path), `crates/veltc/tests/std_tests.rs` runs `velt test std/` with the `tests/std/` suites (a
change to a std test file selects only that test, `cargo xtask affected`), `scripts/package.sh`
and `package.ps1` drop them from the packaged std, and `std-lint` exempts them from the size and
one-class rules (header `// velt/<module> (tests): …`). The goldens and `tests/std` files that
imported internals became white-box tests (`collections/btree/invariants`, `encoding/utf8`,
`encoding/json/scan`, `jsx/void_elements`, `net/http/fetch/client/target`,
`net/websocket/protocol`); the WebSocket ones talk to a `WebSocket` over a stream whose handshake
the test answers, instead of `packages/http-server`, which std cannot depend on.

### 10. Intrinsics are declared, not magic names

Today std calls about 85 distinct `__intrinsic_<name>` functions (694 call sites in 77 files:
`str_byte_at` 131, `array_with_capacity` 68, `str_byte_len` 49, `array_truncate` 47 …) that are
declared nowhere. Sema catches the prefix before name lookup
(`crates/velt_sema/src/body/expr/builtins.rs`), maps the rest of the name by a hand-written
string table to the `Intrinsic` enum (`hir/intrinsic.rs`, ~153 variants), checks it against a
hard-coded Rust signature (`body/expr/intrinsics.rs`, parameters without names) and lowering
handles it in one large match (`velt_vir/src/lower/intrinsics.rs`). The results: no hover,
completion, go-to-definition or `velt doc`; errors that name the Rust variant
(`` intrinsic `ArraySwap` ``); four lists (enum, names, signatures, lowering) kept in sync by
hand; a local of the same name silently wins. Beside them, 300+ `declare function velt_rt_*`
runtime bindings are written in Velt and checked against the runtime, which is the right model.

The fix, as Rust's `#[rustc_intrinsic]` and Swift's `Builtin` do it:

- `std/lang/intrinsics/` declares every intrinsic in Velt, grouped by area (`array.vlt`,
  `string.vlt`, `atomic.vlt`, `types.vlt` for the compile-time type facts, `simd.vlt`, …), with
  a doc comment and named, typed parameters: `export declare intrinsic function
  arraySwap<T>(xs: T[], i: i64, j: i64): void;`. The declaration is the signature sema checks.
- std code imports them like anything else (`import { arraySwap } from
  "velt/lang/intrinsics/array"`); `lang/` is never importable from user code, so the "std only"
  rule becomes the ordinary visibility rule instead of a name prefix.
- The Rust side keeps one table from declaration name to `Intrinsic`, checked at startup against
  the declarations (a missing or extra one is an ICE in tests, not a silent gap).
- An intrinsic that a package legitimately needs (`array_with_capacity`, byte access to
  strings, `array_truncate`) gets a public, documented std API instead (`Array.withCapacity`,
  `velt/encoding` byte views), as the Velt HTTP server proved for its own needs (#1533). The
  packages of §3 use only those.

Done: `std/lang/intrinsics/` declares the 83 intrinsics std calls in 18 files by area (`array`,
`string`, `simd`, `types`, `compare`, `atomic`, `generator`, `json`, `db`, …; `index.vlt`
re-exports them), with `declare intrinsic function` (`ast::FnSig::is_intrinsic`, additive). A
declaration's parameters are borrowed or copied by their type as a function's start out;
`Mut<T>`, `Owned<T>` and `Copied<T>` (aliases of `T` in `modes.vlt`) mark the ones the
intrinsic modifies, takes over or copies. `crates/velt_sema/src/intrinsic_decls.rs` is the one
table from name to `Intrinsic` (plus `targetFeature` and `anyToPrimitive`, which sema writes out
itself); a call is checked against the declaration (errors say `` intrinsic `arraySwap` ``) and
becomes the same `Call { Intrinsic(..) }` as before, so lowering did not change (the VIR of
every golden and bench program is identical). A declaration the table lacks is an ICE-level
error, and a test reads std's declarations and fails on a missing or an extra one. The
`__intrinsic_` prefix is gone: in user code it is an unknown name, `declare intrinsic function`
outside std is an error, and importing `velt/lang/intrinsics` is the loader's visibility error.
The builtins that are intrinsics without a std declaration (`panic`, `sleep`, `xs.push`, `new
Mutex`, …) keep their signatures in `body/expr/intrinsics.rs`. Packages already had public APIs
for what they need (`xs.reserve(n)`, `xs.truncate(n)`, `xs.length = n`, velt/encoding's
`utf8Length`, `utf8ByteAt`, `utf8Substring`); the database drivers reach the per-type row
decoding and parameter binding (`jsonParseCursor`, `dbBind`) through velt/db, whose functions
call them (§11).

### 10b. Compiler hooks: the `__` functions and methods

The other `__` names in std are the opposite direction of an intrinsic: Velt code the compiler
*calls*. Lowering turns a language feature into a call to a std function written in Velt, which
is the right place for the logic (it is inlined like user code, no Rust in the runtime):
`n.toString(16)` calls `__f64ToString`, a template string over `any` calls `__anyText`, a
`Proxy` trap calls the handler's `__get`/`__set`/`__ownKeys`, `JSON.parse(s) as T` calls
`JSON.__parseFromContext`, `util.inspect` calls a class's `__inspect`. There are 171 such
exported functions and 8 types (in `prelude/`, `lang/`, `test/`, `collections/set`) and 96
methods on std classes; the compiler finds them by name, from 186 string literals in 83
compiler files (`crates/velt_sema/src/body/expr/any_text.rs`, `builtins.rs`, `velt_vir/src/lower`).

What is wrong is the mechanism, not the idea:

- **They leak.** The prelude's exports are globals, so every program can call them:
  `__f64ToString(255, 16)` compiles in user code today, and `__anyText(42)` gets as far as an
  arity error. Methods like `Response.__wholeBody` or `JSON.__parseFromContext` show up in
  completion on public types. The `__` prefix is only a convention.
- **Names are scattered strings.** A renamed or deleted hook is found by a failing program, not
  by the compiler; nothing lists which std functions the compiler depends on.
- They are mixed into public classes, so a class's API and its compiler protocol are one list.

The fix, together with §10:

- Hooks live in `std/lang/hooks/` (grouped: `number.vlt`, `any.vlt`, `json.vlt`, `proxy.vlt`,
  `inspect.vlt`, …), plain functions with ordinary names (`f64ToString`, `anyText`), never
  prelude exports, so user code cannot see them (`lang/` is not importable). A hook that needs a
  class's private state takes it as a parameter or becomes a function in the class's own module
  that the class does not export, instead of a public `__method`.
- The compiler names them in one Rust table (`std_hooks.rs`: hook → `std/lang/hooks/<file>::<fn>`),
  next to the std module table of §5; a test loads std and checks every entry resolves with the
  expected signature, so a rename fails the build, not a user's program.
- Protocol methods that are really part of a public interface stay methods but get real names
  where JavaScript has them (`Symbol.for("nodejs.util.inspect.custom")`-style for `inspect`,
  `ProxyHandler.get`/`set`/`ownKeys` as in TypeScript's `lib.es2015.proxy.d.ts`).
- Not hooks: the 65 native symbols like `velt_std_sqlite__open`, where `__` separates package and
  function in the native ABI (docs/internals/design/native-packages.md). They leave std with the
  drivers.

**Status (commit 7, functions done).** The free functions and types are hooks now: 110 of them in
`crates/velt_common/src/std_hooks.rs`, each with its module, its name and its signature, which
`crates/velt_sema/tests/std_hooks.rs` checks against std (and that no program can name one).
They live in `std/lang/hooks/` (`adapt`, `any_methods`, `any_object`, `any_ops`, `any_text`,
`array`, `array_view`, `class_object`, `iter`, `number`, `process`, `proxy`, `record`,
`syntax`), loaded by the prelude (`std/prelude/hooks.vlt`) except `proxy.vlt`, which comes with
`Proxy`; a few stay next to what they need, unexported or in `lang/` (`lang/proxy/array`,
`lang/this_fn`, `lang/typed_array/core`, `collections/set`). Sema names a hook by its qualified
name (`std/lang/hooks/number::f64ToString`), an identifier or type name no source can write
(`Ctx::std_def`); the globals no longer re-export the proxy and `this` hooks, and the global of
`this` functions loads on its marker line instead of a name. The built-in methods of a value held
as `any` keep a name prefix (`anyStr_trim`, found by `velt_vir` `any_builtin.rs`). `velt test`'s
generated `main` calls the runner's hooks `registerFile`, `registerTest`, `registerAsyncTest`
and `runRegistered` from velt/test's internal files, which the loader lets only the harness
import (`LoadOptions::test_harness`). The JSON hooks (`JSON.__parseFromContext`, the
reader's and writer's) are left to the JSON port.

Left for a follow-up: the `__` *methods* (on `Record`, `Map`, `Proxy`, the typed arrays,
`RegExp`, the fetch bodies, `String`, `Error`, `ThisFn`, the test suite) and the `__inspect`
protocol. Each needs its own change in sema and lowering, which call them as methods: the
internal ones become unexported functions of their class's module taking the object, and the
protocols that programs implement (`__inspect`, which user classes define and `console.log`
calls; a typed array's `__kind`, which a subclass may override) need the public names above,
with `Symbol.for(…)` method keys in sema first.

### 11. Per-type code generation (JSON, equality, hashing, inspect) is a privilege today

A package can write its own JSON scanner, reader and writer. What it cannot do is what makes std's
JSON fast: `JSON.parse<T>` and `JSON.stringify` compile to a decoder and an encoder generated
per type (`__intrinsic_json_parse<T>`, `crates/velt_vir/src/lower/json/`), which write private
fields and build classes without running their constructor, dispatch over every subclass in the
program, and rely on a "serializable" requirement sema infers. Lowering also finds std's reader
and writer by hard-coded name. `deepEqual`/`toEqual`, `Map` hashing and key equality, `inspect`,
`structuredClone` and `Array.includes` use the same std-only per-type generation. So a
third-party serializer, deep-equal, hasher or inspector cannot compete, and that is a language
gap, not a JSON one.

This pull request does not change it (it only moves the engine to `velt/encoding/json`, §3). The
follow-up is one general feature that std then uses like everyone else: compile-time reflection
over a type's shape (fields, optional fields, union members, subclasses) plus a way for a
library to generate per-type code from it, with an opt-in for constructing a type and writing
its private fields. It gets its own design document and issue.
