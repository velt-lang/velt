# Standard library layout

Status: implemented. Issue: [#1946](https://github.com/velt-lang/velt/issues/1946).

## Summary

The standard library is imported as `velt/<area>[/<module>]`. Every module is a folder whose
`index.velt` is its public API, made of named re-exports; every other file is internal to the
module whose folder holds it, and the loader refuses to let user code import it. `std/prelude/`
(the implicit prelude) and `std/lang/` (what implements the language and its globals) are never
imported. The compiler names std modules and the std functions it calls in two tables, and
`scripts/std-lint` checks the layout and quality rules on every change. The contributor rules are
in [CONTRIBUTING.md](../../../CONTRIBUTING.md#the-standard-library); this note gives the design
and its reasons.

## Motivation

The standard library is the API other people build on, and every rename after release is a
deprecation cycle. The structure is therefore fixed by rules a tool enforces rather than by
convention: an area name says what a program does (networking, encoding, time), "internal" is a
fact of the file system rather than README prose, each public name has one import path, and the
compiler finds the std code it depends on through tables a test checks, not through string
literals scattered over its crates.

## Design

### 1. Imports are `velt/<area>[/<module>]`

```ts ignore
import { readFile } from "velt/fs";
import { Deque, BTreeMap } from "velt/collections";
import { Headers } from "velt/net/http";
```

- `velt` is a package name the toolchain provides. The loader resolves `velt/…` to `std/` before
  looking at dependencies (`crates/velt_loader/src/spec.rs`), and `vpm` refuses `std` and `velt`
  as package names ("the package name `velt` is reserved for the standard library").
- `velt/x` is an ordinary package path, so a `velt` type package (declarations generated by
  `velt doc --std --format types`) lets `tsc`, editors and bundlers resolve std imports, and
  `jsxImportSource: "velt/jsx"` works in a stock `tsconfig.json`.
- `velt:x` and `std/x` are not std modules. A `std/x` specifier's error names `velt/x`; there is
  no alias, so docs and examples have one spelling.
- `vitest` resolves to `velt/test`, which has Vitest's API, so a test file written for Vitest runs
  as it is.

### 2. Every module is a folder, and its `index.velt` is its public API

```
std/net/http/
  index.velt        ← the public API of velt/net/http: named re-exports, the module doc
  cookie.velt       ← implementation, owned by velt/net/http
  cookie_text.velt
  fetch/            ← implementation folder (no index.velt), still owned by velt/net/http
  h2/
    index.velt      ← a submodule: velt/net/http/h2
```

1. **A folder with an `index.velt` is a module.** Its import path is the folder's path below
   `std/`.
2. **Every other `.velt` file belongs to the nearest folder above it that has an `index.velt`**,
   and is internal to that module. A file in no module's folder is an error (`prelude/`, `lang/`
   and `std/imports.velt` are exempt, §4, §5).
3. **A folder without an `index.velt` is a namespace or an implementation folder.** A namespace
   holds only modules; an implementation folder sits inside a module and holds its files
   (`collections/btree/`).
4. **`index.velt` holds named re-exports only**: `export { Deque } from
   "velt/collections/deque";`. No `export *` and no code: the file *is* the reviewable public API,
   and `velt doc` documents the module from it. Every name it exports has a doc comment.
5. **No `x.velt` next to an `x/` folder.** The pair is `x/index.velt` (a module) or moves into
   `x/` (implementation).
6. **Every public name has one import path.** If `velt/net/http` exports `Headers`, no other
   module does. Globals (`fetch`, `URL`, `Set`, `RegExp`, …) are also importable from their
   module, the one exception.
7. **Named exports only**: no `export default` in std.

User code (any module not loaded from std, packages included) may import only modules outside
`prelude/` and `lang/`; std code may import any std file by its `velt/` path, and imports a name
from the file that defines it. The loader enforces both (`crates/velt_loader/src/visibility.rs`):
importing an internal file is an error naming the module it belongs to
("`` `velt/encoding/json/scan` is internal to `velt/encoding/json` ``").

Because an index only re-exports, the loader follows a std module's re-exports only for the names
a program imports (`crates/velt_loader/src/wanted.rs`): a program that imports `Deque` from
`velt/collections` loads `collections/deque.velt`, not the B+ tree next to it. A file with effects
beyond its exports (`extend` blocks, augmentations) is always loaded. So nothing needs to be split
into a separate module to keep it out of programs that do not use it.

### 3. Areas

The top level is short and named for what a program does, after Go's `net/http` and
`encoding/json` and .NET's `System.Net.Http`. Names stay Node's where a TypeScript programmer
looks for them (`fs`, `path`, `os`, `process`). An area is usually one module, like a .NET
namespace; submodules exist only for large or optional parts with their own documentation page.

| Module | Contents |
|---|---|
| `velt/cli` | command-line argument parsing |
| `velt/collections` | `Deque`, `PriorityQueue`, `SortedMap`, `BTreeMap`, `ConcurrentMap`, `Set`, … |
| `velt/compress` | gzip, zlib, DEFLATE, Brotli |
| `velt/crypto` | SHA-2, SHA-1, HMAC, HKDF, key exchange, AEAD ciphers, secure random |

| `velt/encoding`, `velt/encoding/csv`, `velt/encoding/json` | Base64, hex, UTF-8; CSV; the JSON engine and `json.Value` |
| `velt/ffi` | what crosses to C functions declared with `declare c` |
| `velt/fs` | file system access, `FileReader`, `FileWriter` |
| `velt/generate` | source generators ([source generators](source-generators.md)) |
| `velt/half` | `f16[]` and `bf16[]` in bulk |
| `velt/hash` | a stable non-cryptographic hash |
| `velt/host`, `velt/host/worker` | `HostRef`, JS values host functions pass; a host build's request queue |
| `velt/io` | `IoError`, WHATWG streams |
| `velt/jsx`, `velt/jsx/jsx-runtime`, `velt/jsx/attrs` | server-side rendering of JSX, the JSX provider, the HTML attribute types |
| `velt/math` | integer helpers, `BigInt` |
| `velt/mem` | facts about how values are stored, `Arena` |

| `velt/net/url`, `velt/net/websocket` | `URL`, `URLSearchParams`; the WebSocket client and a `WebSocket` over an upgraded stream |
| `velt/ops` | the interfaces of the operator methods, for generic code |

The modules and their pages are listed at [veltlang.com/docs/std](https://veltlang.com/docs/std/).

### 4. `prelude/` and `lang/` are never imported

- `std/prelude/` is the implicit prelude. Its load order is the explicit list of imports in
  `std/prelude/index.velt`, which the loader follows (`velt_common::std_modules::prelude_order`);
  a test checks that the list names every prelude file once. `std/prelude/global/` holds the
  globals loaded on a condition (see [lazy std](lazy-std.md)).
- `std/lang/` holds what implements the language and its globals, which no program imports:
  `symbol`, `proxy`, `record`, `this_fn`, `import_meta`, `dom_exception`, `typed_array`, number
  parsing, the sort algorithms, the compiler's intrinsics (§10) and hooks (§10b), and more. Since
  nothing imports `lang/`, its folders need no `index.velt`; `prelude/global/*.velt` re-exports
  from it.

### 5. The compiler names std modules in one table

`crates/velt_common/src/std_modules.rs` is the table of the std modules the compiler looks into.
Each entry names a module by its path below the std root (`lang_proxy => "lang/proxy"`); the macros
`std_module!`, `std_item!`, `std_dir!` and `std_specifier!` spell its canonical path, a
definition's qualified name, its folder prefix and its import specifier as literals, and a test
checks that every entry names a file of `std/`. A std file the compiler looks into moves with its
entry there, never with a string literal elsewhere. The same module holds the prelude's order
(`prelude_order`) and the visibility rule (`importable`, `owner`), which the loader and the
language server share, so the editor offers exactly the modules a program may import.

**Conditional imports.** std's map of `#name` imports is `std/imports.velt`,
`export const imports: Imports = { … }`, the same data as a package's `imports` field, read only
when a std module imports a `#name`. It is a std file rather than a compiler table so that std
authors change it beside the variants, and the packaged std carries it. Its `#name`s resolve only
in std's modules; a variant is an internal file, never an `index.velt`, and the variants of one
name export the same API (`crates/velt_loader/src/variants.rs`, run by `velt check --std`,
`velt test` and the editor). `fs/fd/darwin.velt`, `linux.velt` and
`unsupported.velt` are the `#fd-system` variants, for example.

### 6. Quality rules

| Rule | Limit |
|---|---|
| File size | 400 lines, not counting doc comments (`/** … */` blocks; `//` comments count). Files generated by a script say so in their header (`generated by scripts/…`) and are exempt. |
| One exported class per file | named after it (`Deque` in `deque.velt`), with its small companions (an options interface, a result union, its iterator); a module's few error classes may share `errors.velt`. |
| Header | The first line is `// velt/<module>: <role>` in an `index.velt` and `// velt/<module> (internal): <role>` elsewhere; `// velt/<module> (tests): …` in a test file, `// Prelude: …` and `// Global …` in the prelude. |
| Errors | One error class per module, or a few in `errors.velt`, extending `Error`. |
| Names | Files and folders `snake_case`; `*Sync` for blocking twins; Node's name where Node has the function. |
| No duplicate exports | Rule 6 of §2, across all `index.velt` files. |
| Tests | Every module has tests: an end-to-end test that imports it (`tests/golden`, `tests/std`) or white-box tests in its folder (§9). |
| Unsafe code | Each `unsafe { … }` and each unsafe function or method has a comment saying `SAFETY:` in the comment lines directly above it (an unsafe function: or an `Unsafe:` paragraph in its doc comment), the rule c-ffi.md "`unsafe` blocks and functions" sets for packages. |

The size limit only detects a problem; files are split by responsibility, never by line count:

- **A class gets a file of its own**, named after it, with its small companions.
- **Free functions group by the operation family they implement**, the way Node's documentation
  groups them: `velt/fs`'s descriptor functions are `fs/fd/open.velt`, `read.velt`, `write.velt`,
  `sync.velt`, with Node's argument checks in `fs/fd/args.velt` and the errno mapping shared by
  the area in `fs/errors.velt`.
- **Native bindings** (`declare function velt_rt_*`, `declare c("c") function`) sit in one file
  per module (`rt.velt` or `system.velt`), so a module's native surface is reviewable in one
  place and its other files are plain Velt.
- **Helpers two files need** become a file of their own that both import.
- **Tables** (constants, generated data) are files of their own.

The packages in `packages/` follow the same size, class and API-file rules (`src/lib.velt` or a
folder's `index.velt` only re-exports).

### 7. Enforcement

`scripts/std-lint/main.velt`, written in Velt, checks the rules of §2 and §6 and the module tests
(`tested.velt`), and the `// SAFETY:` rule (`safety.velt`, found by text; veltc's
`native::unsafe_sites` std test checks it over the parsed modules too, and on std both find
the same sites). `cargo xtask precheck` (the pre-push hook) runs it on the changed std files and the gate
on all of std. Each message says what to do, not only what is wrong:

| Rule | Message (example) |
|---|---|
| `unowned` | `directly in std/: std files live in a module folder (a folder with an index.velt); move it into its area` |
| `pair` | `x.velt sits next to the folder x/: make it x/index.velt (a module) or move it into the folder` |
| `oversize` | `612 lines besides doc comments (limit 400): split it by type, one exported class per file, helpers in files of their own` |
| `multiClass` | ``exports 2 classes: one exported class per file, named after it (`Deque` in deque.velt)`` |
| `indexCode` | `index.velt is the module's API, only named re-exports: move … into a file of the module and re-export it` |
| `exportStar` | `` `export *`: re-export by name, so the module's API is reviewable in its index.velt `` |
| `defaultExport` | `std modules have named exports only` |
| `header` | ``the first line must start with `// velt/…` (run `velt run scripts/std-lint/main.velt --fix-headers`)`` |
| `duplicateExport` | `` `Headers` is exported by velt/… too: every public name has one import path `` |
| `safety` | ``line 32: unsafe code without a `// SAFETY:` comment directly before it (…); a call that `velt fmt` wraps past 100 columns moves `unsafe {` below its comment: bind the call's arguments to locals first`` |

Existing violations are listed in `scripts/std-lint/allow.velt`. The list only shrinks: with
`--base`, the lint rejects entries the base revision did not have, and without files it reports
entries that are fixed already.

### 8. Libraries live outside std

std is the core. Database drivers and the HTTP server are packages under `packages/`, written
only on public std APIs, so that anyone could write them: `packages/sqlite` (the driver and the
pure-Velt engine), `packages/postgres`, `packages/redis` and `packages/http-server` (HTTP/1.1,
HTTP/2, TLS; `serve` with web-standard handlers, and a WebSocket server). Each has `src/lib.velt`
(its API, named re-exports), `tests/`, a `README.md`, and `native/` and `docs/` where it needs
them; `crates/veltc/tests/packages.rs` runs `velt test` in every package. What the drivers and the
server need from std is public API: `velt/db` decodes rows and binds parameters, `velt/net/http`
has the server-side parts of `Request` and `Response`, `velt/net/http/h2` the HTTP/2 framing, and
`velt/dev` the graceful stop on reload.

### 9. White-box tests

- **Black-box tests** of the public API are end-to-end tests under `tests/golden/std/` and
  `velt test` suites under `tests/std/<module>/`.
- **White-box tests** live next to the code as `std/<module>/<name>.test.velt` (Vitest's
  convention, which `velt test` follows). The loader loads them as std code when `velt test`'s
  harness imports them, so they may import internals; no other module outside std may.
  `crates/veltc/tests/std_tests.rs` runs `velt test std/` with the `tests/std/` suites,
  `scripts/package.sh` and `package.ps1` leave them out of the packaged std, and `std-lint`
  exempts them from the size and one-class rules.

### 10. Intrinsics are declared

Compiler intrinsics are declared in Velt in `std/lang/intrinsics/`, grouped by area, each with a
doc comment and named, typed parameters (`@intrinsic export declare function arraySwap<T>(xs:
Mut<T[]>, i: usize, j: usize): void;`); std code imports them like any function. The declaration
is the signature calls are checked against, and `crates/velt_sema/src/intrinsic_decls.rs` is the
one table from name to `Intrinsic`; a test checks that both name the same ones. `velt/lang` is
internal, so programs and packages cannot import intrinsics: what they legitimately need gets a
public API (`xs.reserve(n)`, `xs.truncate(n)`, velt/encoding's `utf8ByteAt`). The full design is
in [intrinsics](intrinsics.md).

### 10b. Compiler hooks

The opposite direction of an intrinsic is std code the compiler *calls*: lowering turns a language
feature into a call to a std function written in Velt (`n.toString(16)` calls `f64ToString`, a
template over `any` calls `anyText`, `JSON.parse(s) as T` calls `jsonParseFromContext<T>`). These
hooks are plain functions with ordinary names, never exported to programs; most live in
`std/lang/hooks/`, and the few that need a module's internals sit in that module (the `RegExp`
string methods in `std/text/regex/string_methods.velt`). The compiler names them only through
`crates/velt_common/src/std_hooks.rs`, whose entries give each hook's module, name and signature;
`crates/velt_sema/tests/std_hooks.rs` checks every entry against std and that no program can name
one. Sema reaches a hook by its qualified
name (`std/lang/hooks/number::f64ToString`), which no source can write (`Ctx::std_def`).

Protocol members that programs implement or that classes keep private are keyed by symbols rather
than reserved names (`std/lang/hooks/keys.velt`): a custom inspect is the method keyed by
`Symbol.for("nodejs.util.inspect.custom")`, as in Node, and the members the compiler calls on
`JsonValue` or `Map` are keyed by std's own symbols (`[MAP_CURSOR]()`), which no program can name.
std has no `__` names in its public surface.

`velt test`'s generated `main` calls the runner's hooks in velt/test's internal files, which the
loader lets only the harness import (`LoadOptions::test_harness`).

### 11. Per-type code

`JSON.parse<T>`, `JSON.stringify`, deep equality and printing need code per type. A library
writes such code with [source generators](source-generators.md) (`velt/generate`) and reads
dynamic values with `velt/reflect`, the same facilities std uses where it has moved its per-type
code to them.

## Alternatives considered

**`velt:` specifiers.** A scheme prefix marks std imports clearly, but `tsc`, editors and bundlers
cannot resolve it, so `velt check --ts-compat` would have to reject every std import. `velt/x` is
an ordinary package path that a type package can satisfy.

**Implementation in `index.velt`, or `export *`.** Either hides the module's API in other files or
mixes it with code. Named re-exports keep the API in one reviewable list and let the loader load
only the files a program uses.

**A compiler table for conditional imports.** Keeping std's `#name` map in `velt_common` would put
it away from the variants and outside the packaged std; `std/imports.velt` has the package form.
